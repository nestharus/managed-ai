# Library migration and current source maintenance

For a Managed AI store, [the instance contract](../../INSTANCES.md) identifies its ordered catalogues and domain descriptors. Read the selected ID with `engine/knowledge.py --store STORE show SOURCE_ID`. For a change, update the registered owner, qualify the affected descriptor and use reviewed configure at each intended receiver. The library migration below records the earlier authoring arrangement.

## Earlier library entrance

For that edition the general entrance was the short [overview](README.md) and the callable knowledge adapter. Agent understanding and research continuation use the same expandable complete-body library. The former `agent/` folder and research startup files become compatibility routes. They are no longer separately maintained general manuals or independent products. The independently usable products remain the human explanation and the prototype, which includes this complete standalone knowledge folder.

This changes the distribution arrangement, not the canonical research method or earlier evidence. Original accepted releases, historical source identities, published human bodies, exact occurrence archives and recovery maps retain their bytes and scope. The research tree remains current authoring, instrument and history custody. Storage at a research path does not create a separate general agent/research entrance.

## Exact body ownership

The eight former agent manual bodies are preserved in `sources/agent/` as complete `.txt` sources. Publishing therefore reads the complete source owner and never silently replaces it with the small compatibility stub now occupying the historical path.

The transferred bodies retain their original explanations and examples exactly. Older statements appointing four independent arms are historical distribution references superseded by this migration and the current artifact boundary. Do not treat those passages as fresh authority to recreate the retired layout. Future revisions to operating knowledge belong to the nominated source owner and receive new body/library digests. Retain earlier accepted editions where an actual use depends on exact prior text.

The source map collects complete current, evidence and pattern Markdown bodies, research operation descriptions, selected prototype contracts and human communication routes. It records references without rewriting the source text or automatically acquiring every linked history/code body. A description of an operation and its executable implementation are distinct contributions. Product selections declare the actual complete bodies and external participation they need.

## Publish a current edition

`publish.py` is an explicit authoring operation. It reads a nominated current project tree, constructs full objects and a catalogue in a fresh directory, and activates nothing. From the complete project's root:

```bash
python3 -B prototype/knowledge-system/publish.py --root . publish --edition next-accepted --output /tmp/next-knowledge
python3 -B prototype/knowledge-system/knowledge.py --library /tmp/next-knowledge verify
python3 -B prototype/knowledge-system/publish.py --root . audit --library /tmp/next-knowledge
```

Use a fresh output directory. A retry with the identical complete catalogue and object membership verifies the existing result and returns `already-present-verified`; a different or incomplete publication is refused without overwrite. `--overlay PATH` can nominate a reviewable proposal tree over the base during construction; the audit must use the same basis or the adopted complete project afterward. The publisher does not claim an atomic concurrent source snapshot. Quiesce accepted publication or retain the selected source edition when that boundary matters.

After review, the authorized owner adopts the complete library into the next candidate, binds its product manifest and source packet, and explicitly activates the accepted project/engine where required. Keep previous accepted trees intact. A product recipient needs no source sibling directory at use time. An author preparing a later edition does need the nominated current owners.

To revise a module, edit `source-map.json` with the actual receiving purpose, complete `members`, explicit `requires`, meaningful `parents` and justified `external_participation`, then publish a fresh edition. A parent is not automatically a dependency. A required member absent from the selected current sources blocks publication; it must be supplied or the proposed contribution revised explicitly.

The distribution gate treats `human` and `prototype` as current standalone products. Compatibility entrances may link into the complete project and are checked there. It still verifies the protected canonical method, source identities, published originals and exact archived path map. It additionally verifies that every delivered knowledge body matches its declared object and nominated current owner, and that required module closure is available. A product manifest records current products separately from compatibility/storage roles.

Source packet 07 keeps its stable public identity while becoming the knowledge-system entrance packet. It needs this short overview, contract, research continuation route, migration/source-owner account and exact current library acquisition route; it no longer presents a separately maintained full agent manual. Full bodies remain in the prototype product rather than being summarized away. The parent release operation must bind its exact local source map and current accepted edition.

These checks establish declared packaging and identity. A capable receiving use remains necessary to determine whether the knowledge and supplied host actually support the promised work. New findings can change the module boundary, outside participation, source explanation, product promise or runtime arrangement.
