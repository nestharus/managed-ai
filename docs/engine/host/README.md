# Continuing-work host

This optional adapter repairs an enrollment and continuation gap in extended research and construction. It makes the original commission, explicit owed duties, current selected sources, forecasts, changed-source notices and nominated overlaps actual inputs to the native producing context. It uses the existing runtime for source capture, Attention, retained returns, guarded publication and goal interpretation. It does not add a model client, universal planner or domain ontology.

For repeated broad, local or joint observing work, the optional [continuing observation adapter](SIGNAL-FIELD.md) serves supplied receiving uses through [the signal queue](../../../src/managed_ai_information/host/signal_field/queue.py). Domain data supplies the observing agreement, exact source dependencies and live, historical or occurrence lifetime; the adapter carries eligibility across changes and restart, fences stale returns and exposes bounded recovery. A capable host must actually invoke the worker, receive its semantic result and apply accepted domain updates. Its service state neither fulfills the original commission nor grants native effect authority. See the domain's current field for meanings, qualified coverage and remaining work.

## Start one continuing commission

Use a new host root outside the delivered system. An `init` specification supplies an absolute `engine` path to the delivered `runtime/manage_store.py`, the exact `commission` file, and `duties` as `{id, text}` objects. The initial host receipt records enrollment only. The actual capable participant must read each producing context.

```bash
python -B host/continuing_work/continuing_work.py --root /absolute/work/novel init --spec /absolute/init.json
```

Keep this host root for successive narrower contributions. Starting a new unrelated runtime with a narrowed goal does not carry the earlier commission. The adapter cannot recover a duty that was never supplied.

When actual instructions change, `commission --spec FILE` explicitly supplies the new `path`, a continuation `account` and any additional `duties`. Earlier duties remain enrolled; a conflicting rewrite of an existing duty is refused. Changing the original commission file without this operation makes the next prepare or receive refuse rather than silently accepting stale instructions.

For a regenerated host/guidance release, `upgrade --spec FILE` takes the explicit installed `engine` path and an `account`. This bounded route verifies identical native Python program sets and reads the same current goal through both engines before selecting the new path. It retains exact old/new engine, current host and current method identities. Native-code migration requires its own receiving arrangement. Each new preparation selects the method shipped with the actually invoked host under an immutable versioned work path; it does not rewrite methods in earlier captured contexts. Earlier adequate work stays receivable under its original applicable inputs, while actual changed semantic sources still require reentry.

## Keep the continuing inquiry bound to current duties

New hosts bind `continuing-commission` to both the exact commission and
`records/goal.json`. A later goal change can therefore deliver `changed-basis`
instead of presenting an earlier treatment as applicable to unchanged inputs.
This is a nomination for interpretation: it neither infers fulfillment nor
declares the earlier account false.

For an existing host enrolled before that dependency was supplied, use the
explicit `bind-continuation --spec FILE` route after selecting this host
producer. The specification contains a fresh `id` and a nonempty `account`:

```json
{
  "id": "continuation-goal-binding-01",
  "account": "The continuing question depends on current duties as well as the commission; preserve its earlier accounts and add the missing declared dependency."
}
```

The operation obtains one item-filtered native feedback and preserves the
actual current question, use, groups, active flag and additional basis paths.
It adds only the missing goal path through native `track`. It retains the
observation and binding result without changing the goal, old receipts or old
feedbacks. If the dependency already exists, no redundant track revision is
created. The observation itself does not credit semantic consideration.

The next actual preparation delivers the changed question for receiving.
Read the current goal alongside applicable evidence and supply a new public
account through the ordinary receiving or capture route. A goal-independent
external effect, or a changed meaning with unchanged bytes, still requires an
explicit source relationship or updated semantic account. This binding is not
an automatic reconciliation of arbitrary prose or a schedule of all open work.

## Prepare, construct and receive

A `prepare` specification contains `id`, `task`, `prediction`, `duty_ids`, `sources`, and `outputs`. Every source has a stable `id`, current absolute `path`, and an optional `role`. Use `role: producer` for a prompt, operation, model, source-selection policy or executable that actually produces the contribution. Output names are new local filenames. Optional `reads` and `writes` name shared resources; `relations`, `treatments` and `unknowns` retain the participant's semantic interpretation. Optional `questions` is a list of objects with the exact fields described below. Native `techniques`, `discovery` and `compositions` selections can pass through unchanged.

Each question object accepts only `question`, optional `use`, and optional
`sources`. `question` and a supplied `use` must be nonempty text. When `use` is
omitted, it defaults to this preparation's `task`. The following complete
example binds the question to two resources selected in the same preparation:

```json
{
  "id": "alternative-study",
  "task": "Compare a possible arrangement before committing its realization.",
  "prediction": "A small contrast can expose the consequential relation.",
  "duty_ids": ["whole-contribution"],
  "sources": [
    {"id": "entering-prospect", "path": "/work/entering-prospect.md", "role": "producer"},
    {"id": "exact-input", "path": "/work/exact-input.md"}
  ],
  "outputs": ["comparison.md"],
  "questions": [{
    "question": "What would this alternative change?",
    "use": "Compare the consequence before committing the full artifact.",
    "sources": ["entering-prospect", "exact-input"]
  }]
}
```

Supply actual enrolled duty IDs and existing absolute source paths. Within a
question, `sources` is a list of distinct string IDs from this preparation's
selected `sources`; it contains IDs, not file paths. Every named ID must resolve.
The host maps those IDs to their native resource work paths as the question's
`basis`. A subset binds only that subset. Omit `sources`, or supply `[]`, when
the question is intentionally unbound. `source_ids` and `basis` are not aliases
for this host input field.

Unknown question fields, malformed binding lists, duplicate binding IDs and
unselected IDs refuse preparation before source imports, host content changes
or native question enrollment. The CLI still acquires its ordinary sibling
host lock. Validation is local to this question contract and selected resource
identities; it does not close the entire preparation's metadata schema or make
all later preparation failures transactional. Native Attention retains its own
delivery and size bounds. Inspect the actual delivered question and its basis
before relying on that relationship. An earlier malformed occurrence remains
historical; correct the caller's specification in a fresh preparation.

The adapter returns the complete native context path. Read it before producing the output. A source update is imported under a stable native work path, so actual old consumers become stale under existing publication guards. Exact footprint overlaps and shared reads are nominations; a capable participant decides whether and how to split or rejoin work. Disjoint names never certify independence. An unchanged source can gain a new meaning, which requires an authored question or relation rather than a hash-change assumption.

An enrolled question can be selected again without creating a duplicate question
or rewriting its earlier account. Optional `attention_items` selects exact active
native question identities, and `attention_groups` selects caller-defined native
groups. A host question's identity is `<original-scope>-q<number>`; its group is
the original scope. These selectors are added to the continuing-commission item
and this occurrence's new questions. Native Attention retains the applicable
considered/deferred account, validates active identities, and delivers the union
once. An unknown item or group refuses preparation rather than being silently
ignored. This is explicit re-selection, not automatic interpretation of a later
operation or of every unresolved dependency.

Optional `attention_limit` and `attention_max_bytes` pass through native delivery
bounds. With no such selection or bound, the earlier default remains: the
commission and new local questions, with an item limit of at least8 and the
native default byte bound. Selected omissions and active questions outside the
view remain disclosed in the actual context and recoverable native view. A
deliberately small limit can omit a selected question; it does not credit its
consideration. Read that delivery account before treating a deferred inquiry as
having reached its next consumer. To carry a known later inquiry, enroll its
question/use and source relationship, retain its actual disposition, and select
that existing item or useful group at the later construction. Do not route the
entire residual source field merely because it remains open.

The host also nominates exact shared source bytes under different labels and actual use of a previously received output. Each notice supplies a compact status and exact receiving identity, not the entire old custody record. `overlap_limit` optionally bounds delivered detail (default8, maximum200). Delivery is ordered first by exact selected received-output use, then affected changed-source consumer, declared write relationship, prepared-or-unreconciled state, and descending preparation time and scope identity. Each category precedes the categories after it; this is mechanical ordering, not a semantic importance score. Changed-source notices and their generated inquiry are independent of this overlap bound. The notice reports omissions and pins a complete recoverable index. Increasing the limit or reading that index is an explicit next selection. Same-path external source changes can resurface prior consumers even if a caller renamed the source ID.

A `receive` specification supplies an actual `reply` path, attributed `producer`, `account`, and `proposals` mapping the selected output filenames to new generated files. An optional native Attention `assessment` can account for delivered questions. The output is retained and then adopted through native current-basis checks. Local receipt never fulfills a parent duty.

```bash
python -B host/continuing_work/continuing_work.py --root /absolute/work/novel prepare --spec /absolute/contribution.json
python -B host/continuing_work/continuing_work.py --root /absolute/work/novel receive contribution-id --spec /absolute/return.json
```

Serial custody operations may surround parallel model construction. The adapter holds a local host lock while refreshing resources and preparing or admitting output. It does not appoint one permanent semantic merger. If publication refuses after receive, preserve the returned contribution and inspect the native result. Prepare a new current receiving occasion; never overwrite the original turn or blindly repeat an uncertain effect.

`status` distinguishes a retained native return that still needs host reconciliation. `resume SCOPE --spec FILE`, with an explicit `account`, inspects the validated actual native return and publication observations. It never repeats receive or a previously attempted publication. It can acknowledge an intact completed publication or publish a still-unattempted target through native current-basis checks. A stale basis or unresolved publication intent instead requires the existing native recovery/reconciliation route or a new current receiving scope.

When a newly discovered relation supersedes a preparation before any candidate is returned, `supersede SCOPE --spec FILE` takes the actual participant's `producer`, an `account` and a later already-prepared `successor`. That successor must retain the selected parent duties. The adapter uses native receive to retain the actual no-output response and marks the preparation superseded; no output, publication or duty fulfillment is manufactured. An existing native return is refused by this route and must instead use ordinary recovery or new current receiving. Original captures remain unchanged.

The selected external source paths are declared current for that occurrence and rechecked before receive, in addition to native checks on captured copies. A late external edit therefore refuses stale admission even if no other preparation refreshed the copy. Historical evidence should use a retained immutable source path. The local lock coordinates this host's operations; it cannot lock unrelated external editors. A file changing after the check is an ordinary external concurrency boundary, not a cross-filesystem atomic promise.

## Retain a complete candidate before revision

When the current experiment or receiving duty needs a complete first candidate,
choose that meaningful boundary before its editorial or receiving operation.
Retain the whole body at that point. Old strings, a later diff or a claim that
the remainder stayed unchanged cannot replace the missing first occurrence.
An already-needed native return or material capture may supply adequate custody;
do not duplicate it merely to use another mechanism.

For an open native turn, the host's scoped `capture` entrance uses the existing
Python `System.assess` operation through a qualified host adapter to bind a complete
candidate as an Attention product. It needs an actually delivered inquiry whose
current public account fits this work. It does not require another native
context or finish the producing turn. Place the complete candidate in the
native working tree, for example `candidates/partial-first.md`, or copy the
actual full body there before revision. Paths in `products` are relative to
that working tree, not the shell directory. Keep it distinct from any guarded
publication target that the current turn is supposed to propose.

Write a receipt with a fresh identity and the actual delivered item identity:

```json
{
  "id": "partial-first-boundary",
  "assessments": [{
    "item": "CURRENT-SCOPE-q1",
    "disposition": "deferred",
    "account": "The complete first candidate is retained before its receiving/editing operation. Its adequacy remains unexamined.",
    "remaining": ["Encounter the retained candidate against the current receiving question."],
    "products": ["candidates/partial-first.md"]
  }]
}
```

This deferred account is appropriate only when it describes the actual state.
The receipt accepts exactly `considered` or `deferred` as `disposition` values.
For actual consideration with remaining questions, use `considered` and supply
those questions in `remaining`. `considered-with-open-questions`, `unaccounted`
and `changed-basis` are computed view labels, not valid disposition inputs.
Use the actual public judgment. Never invent a considered
verdict merely to obtain a snapshot, and never claim delivery of an item that
was not actually supplied. If no existing relevant delivered inquiry fits, use
an adequate existing receiving/material-capture boundary or deliberately
prepare the needed inquiry; this recipe does not authorize a fictitious account.

Write a host specification that identifies that receipt and its actual producer:

```json
{
  "receipt": "/work/partial-first-receipt.json",
  "producer": "actual producing participant"
}
```

Invoke the selected host against the existing host root:

```bash
python -B /installed/managed-ai-information/host/continuing_work/continuing_work.py --root /work/host \
  capture CURRENT-SCOPE --spec /work/partial-first-capture.json
```

Inspect the successful result and retain its exact `attention.object` identity.
It names the immutable receipt, whose `assessments[].products` entries supply
the complete candidate's object identity, byte count and original working path.
The host response includes only that capture, the requested turn's state and
the fact that capture does not close parent duties. It saves the same scoped response under
`captures/CURRENT-SCOPE/RECEIPT-ID.json`. It does not return a parent-duty
inventory; the containing obligations remain available through the producing
context. This is not a whole-goal status or completion judgment.

Use this scoped entrance for a constructor whose exposure is bounded. The
native `system.py assess` command also returns global status, including other
turn/publication names; displaying its raw response can disclose unrelated
history. The host's `capture_native.py` adapter calls the selected Python assessment
under the native owner lock and obtains only that turn's summary. It avoids
the CLI's global-status computation and unrelated packet traversal. The host
retains this selected adapter result and the adapter's identity in owner evidence.
This does not restrict filesystem
access or make global event logs safe to open under a narrow input boundary.
Known receipt-validation and adapter-compatibility errors are returned without a global status body;
other raw native failures stay in owner evidence and receive a scoped
unconfirmed-capture message. Such a failure does not prove that no capture
occurred before a later local result or evidence write failed.
An existing exact capture must be recovered, not blindly replayed after an
uncertain response; native receipt identities remain single-use.

The adapter is qualified to an exact native Python program profile. It verifies
every native Python program before importing the selected engine or recording a
receipt. Any program edit, addition or removal refuses capture until this adapter
is separately requalified. Existing host `upgrade` still requires byte-identical
native programs; this adapter does not weaken that guard. `System.assess` and
selected `Exchange.inspect` keep their supported behavior. Exchange builds the
current transport summary from the selected observations. For earlier qualified
engines the adapter retains the original projection and dispatch-marker check.

The profile check reads a fixed installed program set on each capture. Selected
inspection still validates the selected context and its referenced objects, and
Attention still reads, hashes and writes its growing index metadata. Avoiding
global status does not make the whole capture route independent of every kind
of history or establish a measured wall-time improvement. Ordinary native
`assess` and `status` remain available with their full-status contracts.

Recover the receipt and then its product through the existing supported route:

```bash
python -B /installed/managed-ai-information/runtime/track_attention.py --root /work/host/native/exchange \
  object RECEIPT-OBJECT --text
python -B /installed/managed-ai-information/runtime/track_attention.py --root /work/host/native/exchange \
  object PRODUCT-OBJECT --text
```

The exact body remains recoverable if the mutable candidate is later revised.
A fresh receipt can bind the successor under its actual account; the old receipt
and product remain. Do not overwrite the old receipt or report that capturing
the successor recovered a lost predecessor. Ordinary revision still is not a
generating repair unless changed producing means and an actual new occurrence
support that claim.

This operation retains evidence; it neither returns nor publishes the candidate,
fulfills a parent duty, authenticates the participant, nor establishes literary
or semantic adequacy. Use the ordinary actual return/receiving operation when
the contribution is ready. The cooperative custody mechanism cannot prove that
a participant used it before an undisclosed edit; an omitted boundary remains
an evidence limitation. No full native turn per thought or universal drafting
pipeline is required.

## Maintain shared material and current selections

For repeated source captures, releases and evidence products, `managed_material.py` provides a separate managed-material maintenance route. It reuses raw SHA-256 identities, retains occurrence and current-selection manifests, decomposes historical ZIPs into exact reconstruction recipes, exports a self-contained recovery closure, and supports verified retirement of explicitly selected obsolete copies. See [MATERIAL-MAINTENANCE.md](material_retention/MATERIAL-MAINTENANCE.md) for the encoder boundary, cutoff, recovery and lifecycle contracts. It does not migrate the host or native exchange.

## Retain a failure and exercise changed means

`repair-open` takes `id`, `failure_account`, `causal_hypothesis`, exact historical `inputs` and `failures` paths, and `producer_before` entries `{id, path}`. It retains those bytes. A later `prepare` can name that repair in `repairs`. This original-case route requires the original input bytes and a selected changed producer under the same resource identity. A transfer case uses a separate scope with its actual different inputs; it is not mislabeled a replay.

After the actual output returns, prepare a distinct receiving scope. Select all generated outputs, the original failed outputs, original inputs and actual old/new producing means. A separate attributed participant must encounter them and return an assessment JSON with:

- `finding`: `fixed-within-stated-scope` only when warranted;
- `causal_account`, `comparison`, `transfer_or_rival`: nonempty text containing substantive receiving judgments;
- `limits`: nonempty text, or a nonempty list of nonempty text limits;
- `generated_sha256`: either a list of the exact generated SHA-256 values, or a complete object mapping each generated local filename to its exact SHA-256 value. Named mappings must match both names and bytes.

`repair-accept` takes the repair `id`, `generation` scope, `receiving` scope and returned `assessment` filename. It checks current generated/receiving outputs against their actual received pins and reads the assessment from the retained returned object. A later edit to the visible assessment file cannot become the receiver's judgment. It checks the declared lineage and preserves the receiver's judgment. It cannot tell whether a changed producer merely adds a comment, whether an account is honest, or whether the repair generalizes. Those are actual receiving questions. A changed hash alone is never presented as a semantic pass.

## Account for the whole commission

`duty` can record `open` or `fulfilled` with a current account. Fulfillment must cite actually returned output work paths in `evidence`; the account remains attributed semantic judgment. This route has no release command. `finish` refuses while enrolled duties remain owed and otherwise records the owner's whole-goal interpretation. The ordinary native runtime remains usable directly, so this is an explicit host contract, not an access-control boundary or a claim that every possible caller is forced through it.

`status` returns native custody, scoped returns and repair lineage. Retain the host root, its immutable source objects, native exchange and command events when distributing evidence. Paths in a saved host root may require explicit relocation on another machine; the delivered program itself is relocatable. Actual source bytes, context bytes, generated words, receiving findings and unresolved questions support different measurements and must remain separate.
